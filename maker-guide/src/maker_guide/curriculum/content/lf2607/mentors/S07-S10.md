# S7-S10 Delivery Notes

## Teaching Shape

| Session | Core Experiment | Leave With |
|---|---|---|
| S7, 2026-09-19 | Run personal Caddy, correlate PID and listener, send raw HTTP, and recover three safe incidents | Explained ownership, local/public/static responses, and request-log evidence |
| S8, 2026-09-26 | Hand that backend to systemd, inspect requests, repair one fault, test logout | A working user unit, recovery evidence, and a source copy |
| S9, 2026-10-10 | Refresh report facts automatically, then peer-test the operating instructions | An observed timer run and a recoverable, documented handoff |
| S10, 2026-10-24 | Investigate briefly, choose evidence, demonstrate, plan a next action | An explanation of personally understood work |

Use the time allocations where provided; keep timings in mentor notes only. Keep explanations close to the experiment they support. Ask for predictions before showing expected results. S7 raw HTTP and three incidents are core; publishing, notes, and Git remain optional self-study, not filler to stretch the live session. Do not add drawing exercises or turn optional tmux, text tools, or Bandit into extra prerequisites.

Keep the live lesson independent of application progress. Only the final slide offers bot help between sessions; no bot workflow or validation checkpoint belongs in S7 session material. Keep the two existing graded objective IDs unchanged. Historical completion records are not automatic proof of process/listener correlation, raw HTTP, or incident recovery.

For assessment, the first objective requires only a successful local curl request to the learner's running backend; public/service and static requests remain manual observations, not automated success requirements. Accept an honest diagnosis of DNS or TLS failure before HTTP without demanding an HTTP status that was never received. The second objective requires explanations of the observed behavior and causes in the learner's own words; status numbers or keyword lists alone are not accepted. Neither objective requires published notes, a new page, or Git work.

Preserve the beginner S7 opening: client/server roles, HTTP, why run personal Caddy, loopback and ports, launch, local curl and its log, then the proxy route, public browser request, and visitor logs. Follow with S3's `ps -u "$USER" -o pid,comm,args`, new `ss -ltnp "sport = :$PORT"`, raw HTTP, and three incidents. Defer the proxy explanation until local access works; keep notes, Git, and publishing out of the live sequence.

Always distinguish two processes running the same Caddy software. Shared Caddy is a server to the browser and a client to personal Caddy; personal Caddy answers the forwarded request. Say "classroom machine", "shared Caddy", "personal Caddy", and "instructor", not "Caddy versus your server".

## Before S7

- Verify each learner's assigned port is `10000 + uid`, fits the port range, and matches the provisioned loopback upstream. Inspect existing listeners with the account owner before any interruption.
- Before delivering the all-interface listener example, have an authorized operator inspect the deployed nftables ruleset and every included fragment read-only. Tracked IPv4/IPv6 `inet` input rules default to drop and allow new external TCP connections only on `22`, `80`, `443`, and `6697`, blocking assigned `10000 + uid` ports. Deployment has not been checked; extra fragments may change this. Do not deliver the wildcard example until that protection is confirmed. No firewall changes are part of the lesson.
- Verify static and personal service routing, DNS, and certificates from a laptop network. A public `502` is a useful backend observation only after those prerequisites work.
- Verify Caddy at `/usr/bin/caddy` and the runtime tools in an ordinary consenting practice account. S7 requires `ps` from `procps`, `ss` from `iproute2`, and Debian's OpenBSD `nc` from `netcat-openbsd`, alongside `printf`, `timeout`, curl, and `mktemp`. Package declarations are managed separately; deployed availability and the netcat variant have not been verified. Run `command -v caddy curl ps ss printf timeout nc mktemp` and `nc -h`; confirm `-C` (CRLF), `-N` (EOF shutdown), and `-w` support. Missing tools are operator preflight work, not a learner sudo task or a reason to mark raw HTTP optional.
- In that practice account, use `PORT="$((10000 + $(id -u)))"`, then `caddy file-server --listen ":$PORT" --root "$HOME/public_html" --access-log`. From the second SSH shell, correlate the account-owned Caddy PID from `ps` with the `LISTEN` port and process field in `ss`. Verify local curl, then the bounded raw request from self-study and its log. For optional publishing practice, verify a source change appears without restarting: the publisher replaces `public_html`, and explicit `--root` follows that path on new requests, unlike serving only the working directory.
- Personal Caddy listens on all interfaces; the firewall, not loopback binding, blocks new direct external connections. Shared Caddy still connects to `127.0.0.1` at the assigned port. Keep personal HTTP without `--domain`. Shared HTTPS is already configured; no Caddyfile, JSON configuration, or helper is needed. `file-server` disables its admin API. Tracked Salt configuration isolates shared administration on a private Unix socket; verify the migration is deployed and no shared TCP admin endpoint remains accessible to learners. Do not use `caddy stop` or `caddy reload` in the exercise. Stop the foreground process with `Ctrl-C`, or the supervised process with `systemctl --user stop site.service` only.
- `--root` selects files, not a sandbox. Keep private files and symlinks to them out of the published tree. Without `--browse`, a directory missing its index does not get an automatic listing. Repair the index source and rebuild rather than enabling browsing.
- Keep `--access-log` in every launch and unit. Match `request.method`, `request.uri`, `status`, and a timestamp or time (`ts` in JSON) to actual requests. Do not promise an identical foreground-terminal and JSON-journal layout. Personal Caddy's direct client can be shared Caddy on loopback, not the visitor's own address.
- Preview slides and prepare two SSH connections per learner. Keep core raw-HTTP requests aimed at `127.0.0.1` on the learner's assigned port, not shared Caddy ports. First use `nc -C -N 127.0.0.1 $PORT` interactively: type the request line and `Host` with a numeric port, finish headers with a blank line, then signal EOF with `Ctrl-D` while no input is pending. Distinguish the HTTP terminator from terminal EOF; cancel a stuck client with `Ctrl-C`. Then save `http-request.sh`: `printf '%s\r\n'` supplies the same lines and final empty argument to `timeout 5s nc -N -w 3 127.0.0.1 "$PORT"`. The pipe supplies EOF, so no `Connection: close` header is needed. Change only the path to an absent `/missing.html`; compare response status and access log without modifying any real file.
- Rehearse all three incidents in order: an identical second launch must fail while the original PID/listener and page remain; a fresh empty practice root must produce local/public service `404` with a live PID/listener and logs while static delivery works; restore the original root before stopping it to compare local refusal, public proxy `502`, and working static delivery. Create `practice_root=$(mktemp -d)` only in the first/server shell after stopping the original; use the self-study failure guard. Treat it as public, keep it empty, and never substitute a private tree, delete/rename website files, enable browsing, choose another port, or stop shared Caddy. Recovery controls only the owner's known foreground process with `Ctrl-C`.
- Learners missing S6 artifacts can use the self-study recovery instructions. Do not spend the whole group session reteaching curl or require an automated progress pass before participation.

## S7 Run Of Show

Total: 180 minutes. Timings belong here, not in learner material.

| Elapsed | Minutes | Activity | Evidence |
|---|---:|---|---|
| 00:00 | 20 | Client/server basics, HTTP, personal Caddy, loopback and ports | Learners distinguish programs, machine, and assigned port |
| 00:20 | 25 | Two SSH shells, start Caddy, local curl | Page response and its first access log |
| 00:45 | 20 | Public browser route, proxy roles, visitor logs | Peer request matched by method, path, status, and time |
| 01:05 | 20 | Reuse `ps`, introduce `ss`, correlate ownership | Own Caddy PID matches assigned `LISTEN` port |
| 01:25 | 15 | Break | Leave the known foreground server running |
| 01:40 | 25 | Type HTTP through netcat, save it as a small script, change only path | Distinct blank-line/EOF roles, responses, and matching logs |
| 02:05 | 40 | Occupied port, empty root, restore root, stop/refusal and proxy `502`, restart | Predictions compared with process, listener, response, and log evidence |
| 02:45 | 15 | Explain back and clean up | Real root recovered locally/publicly, then manual process stopped safely |

For cleanup, learners remove only the known empty practice directory with `rmdir -- "$practice_root"` in the first shell. Leave an unknown or nonempty directory alone. Restore any pre-existing S8 user service only after stopping the manual process. Do not compress away raw HTTP or an incident to add optional publishing work.

## Before S8

- Inspect the actual logout policy and `Linger` for each participant, including the practice account. Tracked classroom policy uses `KillUserProcesses=yes` and `UserStopDelaySec=0`, with lingering explicitly enabled for `linux-foundations` members in the reserved classroom UID range. An enabled unit alone cannot guarantee logout survival if that policy has not been deployed. Applying policy remains an explicit administrator operation, not a learner exercise; do not promise persistence until the final-login logout experiment succeeds.
- Agree on an observation interval beyond the deployed logout delay. Close all account logins before the browser observation; reconnecting first invalidates the experiment.
- Prepare one known-good unit backup before changing only `/usr/bin/caddy` to `/no/such/caddy` in `ExecStart`. This still produces an executable failure, often `203/EXEC`. Use only the consenting learner's unit, preserve drop-ins and personal settings, and restore and verify before leaving.
- Keep `WorkingDirectory=%h` and `ExecStart=/usr/bin/caddy file-server --listen :12345 --root %h/public_html --access-log`, replacing `12345` with the assigned numeric port. `ExecStart` is not Bash and cannot calculate the UID formula. Keep working unit copies in `~/src/services/`, outside published pages; no helper script between Caddy and systemd is needed.

## Before S9

- Confirm the current `/docs/guides/resources/maker-report.sh` has strict error handling and temporary-file publication. Have learners back up and compare older copies before accepting a replacement; preserve their personal report additions.
- Exercise the short timer in a practice account. Observe an automatic activation and a changed report date, not only the earlier manual baseline run.
- Confirm a failed report prevents the build, and publication preserves the last valid output on failure. Use isolated fixtures for deliberate collection failures, not learners' live reports.
- Stop the timer and wait for builds before editing source, copying files, or reviewing Git changes. Do not run standalone builds concurrently with the scheduled service.
- Leave the hourly schedule, not the classroom-speed timer. Have peers read the README while owners operate their own accounts; no password sharing.

## Before S10

- Protect 75 minutes for twelve five-minute demonstrations and transitions. Stop the unfamiliar investigation after 20 minutes, even if it remains unresolved.
- Prepare an inspect-only file or an unfamiliar log/option question for learners who do not choose Bandit. Use ordinary text or archive data without secrets or executable payloads.
- Offer fallback commands privately when needed, rather than requiring everyone to perform the same command tour.
- Discuss unfinished work honestly and agree on a realistic next action. Do not require a live outage during the demonstration or publication of a private plan.
