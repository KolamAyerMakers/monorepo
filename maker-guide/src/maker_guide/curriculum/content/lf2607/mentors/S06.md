## Teaching Contract

The priority is making decisions with `if`, not memorizing a networking toolbox. Demonstrate the ping/traceroute warm-up from your classroom SSH session, then have learners connect, follow the web-request path from DNS to HTTP, and build the checker.

Learners already have SSH, Micro, assignments, quoting, `printf`, streams, and a working S5 report. Git homework is not a prerequisite. Retrieve those skills briefly; do not reteach S5 or overwrite a learner's report script.

Three outcomes:

1. Distinguish name lookup, ICMP echo replies, and HTTP responses.
2. Inspect statuses, headers, and a body with curl.
3. Explain and run a checker for the homepage and report, including a report-404 repair and a failed-request branch.

`for` repeats the supplied page arguments. Traceroute is a brief warm-up demonstration; `while` stays in the optional appendix. Raw HTTP over netcat stays in S7.

Teach `for` and `if`, but do not grade their presence or exact nesting. The reference checker is one implementation, not a required copy. Equivalent functions, `case` statements, variable names, page order, and curl flag order are accepted when the output meets the behavioral contract.

## Demonstration Notes

- State the viewpoint before interpreting evidence. `host` queries DNS; curl can resolve through `/etc/hosts`.
- Present ping and traceroute as diagnostic tools, not required steps in opening a page. Use the same numeric public address for both, then introduce the web-request diagram.
- Teach status families before examples. `3xx` is broader than "the resource moved": `304` concerns caching.
- `HEAD 200` is a successful request, not proof that the HTML is correct or freshly generated. Let learners find their actual report heading in `GET` output.
- Make `if` work on one path before adding `for`. Each stage belongs in the same checker file.
- Keep S5's `set -euo pipefail` from the first script. Its `page="$1"` requires an argument; pass `""` for the homepage. Before explicit exit-code capture is added, a curl failure stops the script; afterwards it prints the diagnostic and continues to the next page.
- Evolve `$1` into `for page in "$@"`, not a hardcoded page list. Accept any page paths. Teach that `$#` is zero with no arguments, but one for `""`: no arguments print usage and exit `2`; the empty argument checks home. Normal invocation: `bash ~/scripts/site-check.sh "" maker-report.html`.
- Explain `==` versus assignment `=`, both delimiters `[[`/`]]`, then `elif` and `&&`. Keep examples quoted.
- Reset `curl_exit_code=0` on every iteration, capture HTTP in `status`, and use `|| curl_exit_code=$?` to record failure without triggering `set -e`. The outer `if [[ "$curl_exit_code" -eq 0 ]]` checks curl's exit code; the inner `if` interprets HTTP. Do not turn expected `404` responses into transport failures with `-f`.
- The checker prints messages for humans. Do not use its exit code as the live-health result or claim it is production monitoring.

## Predict, Then Check

Use the hypothetical cases in the [final exercise](../sessions/S06/self-study.md#exercise-6-predict-then-check). Learners read the unchanged checker and predict each diagnostic. Ask why homepage and report `404` cases differ, and why a curl failure skips the HTTP decision. Then run the checker on real pages and follow any repair advice. Do not inject statuses or delete a working page to create a failure.

For a real `404`, run `bash ~/scripts/site-check.sh not-a-page.html` with an unused filename. It must not suggest report regeneration. For a request failure, use the reserved `.invalid` example from the slides with its three-second timeout. Neither requires changing the checker. A proxy may respond; use the observed result rather than promising a specific error message. The controlled guide fixtures exercise connection failures safely, separately from live HTTP responses.

Use the provided report generator when needed; leave learners' committed S5 versions in `~/src` intact. `cp -i` lets them keep an existing working copy in `~/scripts`.

## Guide And Completion

Three live gates: observe DNS command, observe homepage header command, and pass the checker's simulated cases. For the current checker task, CLI `guide now` and `guide check` automatically request the local suite, which executes the script with varying page arguments and a separate no-argument usage case under the invoking learner's UID. The daemon never executes the script. IRC must direct learners to these commands in the classroom shell, not ask them to submit source or output as a substitute.

Four reinforcement quests: DNS answer line, ping summary (including no replies), HTTP status line/header, and the same checker behavior. Run `guide now` before starting quest work. Use `guide answer 'observed text'` when asked for observations; the checker quest instead runs the local suite.

| Simulated case | Feedback target |
|---|---|
| Both pages return `200` | Identify both successful responses. |
| Report alone returns `404` | Diagnose report `404`; suggest `maker-report.sh`, then `build-website`. |
| Homepage alone returns `404` | Diagnose homepage `404`; do not suggest report regeneration. |
| Report `500`, homepage `200` | Diagnose the HTTP error, not success. |
| Homepage transport failure | Diagnose failure and still check the report. |
| Report transport failure | Diagnose failure and still check the homepage. |
| Report curl emits `200` but exits nonzero | Diagnose failure despite the emitted status. |
| Arbitrary missing page alone returns `404` | Identify the path and `404`; no report regeneration. |
| No arguments | Usage help and nonzero exit, without a page request. |

Each page needs its URL or a homepage/home page/report label on the diagnosis line or a preceding heading; identify other pages by their path or URL. HTTP results need the actual code and diagnosis; transport failures need clear error, connection, DNS, TLS, or timeout wording. No failure may also be claimed as success. Report repair advice must name both commands, but exact sentences are not required. Use the fixed case feedback rather than asking learners to match the reference source.

The suite redirects the allowed personal URLs to loopback fixtures through a native-curl PATH shim. It runs with a sanitized environment and bounded time/output, but it is not a sandbox: scripts retain the learner's permissions and can have side effects or bypass the shim. Never run a learner's script as root, as the daemon, or on their behalf. The result stays bound to the task and source hash on the same authenticated connection; edits during checking require a rerun. Raw stdout/stderr and source are not submitted as grading evidence or sent to the LLM; feedback is fixed per case.

A simulated pass does not verify live site health or external reachability. The instructor still checks explanations, `bash ~/scripts/site-check.sh "" maker-report.html` against the real site, and both pages in the laptop browser. Do not clear or regrade existing stored completions to demonstrate the new checker.

## Recovery

- Missing command or privileges: operator handles provisioning before class.
- Missing report generator: copy the provided script; do not reconstruct the learner's website.
- Syntax error: `bash -n`, inspect delimiters, then `bash -x` after parsing succeeds.
- Report `404`: regenerate Markdown, rebuild HTML, retest. Homepage `404`: inspect `index.md`, then rebuild.
- TLS, `403`, `500`, or `502`: keep the exact output and escalate shared-service issues.
- Wrong URL twice: inspect `url="$base_url/$page"` inside the loop.
- Guide simulated pass but failed live page: repair and retest the page; simulated completion did not assert live network success.
- Local suite unavailable or old CLI: ask the operator to deploy the matching updated CLI and daemon; do not fall back to source inspection or privileged execution.

Do not reset progress, remove source, or repair learner files as root.
