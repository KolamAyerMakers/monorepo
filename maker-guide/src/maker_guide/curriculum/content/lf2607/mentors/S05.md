# S5 Instructor Runbook: Make The Shell Work For You

Session: S5

Saturday, August 29, 2026, 13:00-16:00 Asia/Singapore.

## Teaching Contract

The session is successful when most learners publish a report generated by one Bash script they built in stages. Syntax coverage is not the goal.

Four live outcomes:

1. Save known commands in `~/scripts/maker-report.sh` and run the file with Bash.
2. Explain `./`, read the owning user's permission triplet, add `u+x`, and use the shebang for direct execution.
3. Pass one quoted title through `$1`, `report_title="$1"`, and `"$report_title"`.
4. Make the script write `~/src/pages/maker-report.md`, then publish `maker-report.html`.

Assume learners can use SSH, paths, Micro, `cat`, `ls -l`, redirection, pipes, `chmod u+x`, and `build-website`. Retrieve those skills instead of assuming fluent recall after the three-week gap.

New syntax is limited to `bash`, `bash -x`, `bash -n`, `printf`, one argument, one variable assignment, a shebang, direct paths, and one brace group with one redirection.

Do not teach `read`, environment inheritance, `$?`, combined strict mode, `pipefail`, `$#`, `"$@"`, conditionals, loops, functions, or command substitution in the live core. The final script intentionally expects one title argument. S6 introduces explicit failure handling through a site checker, not changes to this report generator.

An unscored appendix may demonstrate `set -u` and `set -e` separately after the core. Do not add either option to the report script and do not describe `-e` as "stop on every error."

## Live Demonstration Sequence

### Save, Run, Trace

Ask learners to predict the output of `whoami`, `hostname`, and `date`. Create the exact commented file from the slide in Micro, clearly separating prompt input from editor contents. Tell learners to copy `#!/bin/bash` now and explain it after the permission experiment.

After `bash maker-report.sh` succeeds, reveal the execution sequence:

```sh
bash -x maker-report.sh
```

Point at one `+` trace line and its following stdout. Do not expand into tracing options.

### Make Permission Denied Useful

From `~/scripts`:

```sh
./maker-report.sh
```

Expected diagnostic: `Permission denied`.

Explain `./` as the path to the file in the current directory. It identifies a file but grants no permission.

Inspect and split the permission string into file type, owning user, group, and other triplets. The learner created the file, so `u` refers to that learner:

```sh
ls -l maker-report.sh
chmod u+x maker-report.sh
ls -l maker-report.sh
head -n 1 maker-report.sh
./maker-report.sh
```

Read `u+x` as owning user, add, execute. Then explain that the existing `#!/bin/bash` first line tells Linux to use Bash. Do not remove the shebang for another experiment; it adds a second failure mode without helping the beginner model.

### Make Assignment Visually Exact

Type this without alignment diagrams:

```bash
report_title="$1"
```

Then show the wrong form and its consequence:

```bash
report_title = "$1"
```

Spaces cause Bash to interpret `report_title` as a command. Do not format `=` as if whitespace were optional.

### Isolate The Two Quoting Problems

Keep the expansion quoted while changing only the call:

```sh
./maker-report.sh My Maker Report
./maker-report.sh "My Maker Report"
```

Expected probe output: `title=<My>` and `title=<My Maker Report>`.

Then keep the call quoted while changing only the expansion inside the script:

```bash
printf '# %s\n' $report_title
printf '# %s\n' "$report_title"
```

The first form produces three Markdown headings. Restore the quoted expansion immediately.

### Read The Markdown Before Generating It

Point to the opening triple backticks, the optional `text` label, and the closing triple backticks. Do not use tildes as an alternate fence in this session.

Rebuild the pipeline at the prompt:

```sh
cut -d: -f7 /etc/passwd
cut -d: -f7 /etc/passwd | sort -u
```

Call the result "shell fields in local `/etc/passwd` entries". Classroom learners may come from SSSD and are not enumerated by this file.

### Reveal One Grouped Redirection

First run the complete report body without braces so learners can inspect stdout. Only after the shape is correct, add:

```bash
{
  # existing report commands
} > ~/src/pages/maker-report.md
```

Explain one idea: the braces make several commands one output source, so one `>` writes the entire file. Keep `build-website` outside the script because its logs are not report content.

### Debug In Layers

Require this order:

```sh
cd ~/scripts
bash -n maker-report.sh
./maker-report.sh "S5 Report"
cat ~/src/pages/maker-report.md
build-website
ls -l ~/public_html/maker-report.html
```

If generation fails, use:

```sh
bash -x maker-report.sh "Debug Report"
```

The report stdout still goes to the file. The trace remains visible on stderr.

`bash -n` parses the script without executing it and normally prints nothing on success.

## Expected Errors

| Error or observation | Likely cause | Intervention |
|---|---|---|
| `No such file or directory` | Wrong directory or unsaved Micro buffer | Run `pwd`, `ls -l`, and `cat` before editing again |
| `Permission denied` | `x` is missing from the owning user's triplet | Inspect with `ls -l`, then add only `u+x` |
| `maker-report.sh: command not found` | Bare name searched `$PATH` | Use `./maker-report.sh` from `~/scripts` |
| `bad interpreter: /bin/bash^M` | CRLF first line | Recreate the first line in Micro on the VM |
| `report_title: command not found` | Spaces around assignment `=` | Restore `report_title="$1"` exactly |
| Script prints only `My` | Call title was not quoted | Compare the two call forms |
| Script prints three headings | Variable expansion was not quoted | Restore `"$report_title"` |
| Markdown fence appears as text | Backticks are missing or mismatched | Restore the opening fence with its `text` label and the closing fence |
| Markdown file is empty or partial | A grouped command failed after `>` opened the file | Run with `bash -x`, repair the last traced command, then rerun |
| Markdown contains build logs | `build-website` was put inside the group | Remove it and run it separately |
| `~/src/pages` missing | Site absent or source subdirectory deleted | If `~/src` is absent, run `build-website`; if the class marker exists, run `mkdir -p ~/src/pages`; otherwise stop |
| Progress did not advance | Required evidence was incomplete when the final command ran | Inspect the objective, repair its file or mode, then rerun its final command |

Never repair learner files as root. Do not make the bot execute learner scripts. The validators inspect bounded files, modes, built output, and successful command observations.

## After The Live Core

Fast learners should run `guide now` before starting reinforcement. Quest evidence is accepted only after assignment.

The three quests deliberately do different work:

1. Extend the useful report with uptime and republish it.
2. Practice a home-anchored script path from `~/playground`.
3. Copy the final executable into `~/src/scripts` and prove it exists in Git history.

The two appendix slides form a separate 15-minute lab. Use them only after the four objectives and only when time extends beyond the three-hour plan. Otherwise point learners to the optional self-study section. The lab must remain in `~/playground/options-demo.sh` and must not alter the scored report generator.

Teach the appendix in this order:

1. With only `set -u`, run without `$1` and observe the `unbound variable` diagnostic.
2. Run with a title; the failed `ls` is followed by `after failure`.
3. Add `set -e`, rerun with a title, and observe that `after failure` disappears.
4. State the limit: this standalone failure exits a straight-line script, but control-flow lists and pipelines have exceptions.

Do not publish raw shell history. It can contain secrets, private paths, and accidental credentials.
